- **Status bar vs notch** (fixed 2026-11-19): Phosh/gmobile 0.4 finds the panel cutouts by device-tree compatible (`qcom,kona-mtp` here) in `/org/gnome/gmobile/devices/display-panels/<compat>.json`; the base rootfs already overlays that path with `/var/lib/droidian/phosh-notch` but the directory was empty. In build_droidian_install.py (NOTCH_JSON).
- **Vibration** (fixed 2026-11-19, flashed to `boot` as kernel #11 (sha fc1f5207…), user-confirmed in menus, lock screen and buttons): the Oplus vibrator HAL needs `/sys/class/leds/vibrator/trigger` = `transient` (odm `vibrator-default.rc`), but the kernel lacked `CONFIG_LEDS_TRIGGER_TRANSIENT` (now in droidian.config). Enabling it alone made the phone hang ~1 min after boot: ledtrig-transient's timer (softirq) calls `led_set_brightness_nosleep()` -> `aw8697_haptic_brightness_set()` which takes a mutex and does I2C -> `BUG: scheduling while atomic` in `transient_timer_function`, then the i2c_geni bus times out and the SoC locks up. Fix: register the aw8697 callback as `brightness_set_blocking` (returns int) so the LED core runs it from a workqueue (kernel commit on branch `droidian`). Dead ends: writing `activate`/`duration` by hand and `service call ...IVibrator/default 3` did nothing without the trigger; the qti-haptics FF input device rejects rumble effects (EINVAL) and is not the real motor. feedbackd still logs failures for the HIDL vibrator/light HALs but vibration comes through the Awinic path. The `gameopt_hal_service` crash loop (SIGSEGV every ~10 s, `FreqControl::releaseCpuAll`) is still open and harmless.
- **Mobile network falls back to 2G at boot** (fixed 2026-11-19 in `bitra-modem-online`, live-tested, not yet flashed; user report): after every boot the phone showed 4G for a few seconds and then 2G only; Settings sometimes showed "2G, 3G preferred". A per-second poller (ofono RadioSettings/NetworkRegistration + `mmcli`) over a reboot showed: ofono reports `TechnologyPreference = "umts"` (2G/3G, no LTE) from the moment the modem appears (23 s), regardless of the saved `/var/lib/ofono/<imsi>/radiosetting` (`TechnologyPreference=4`); the modem still registers on LTE at 30 s, then drops to GSM at ~44 s; the user's manual 4G selection fixed it. (Airtel here seems to have no 3G, so GSM is what is left.) Fix: after `Online=true`, `bitra-modem-online` sets `RadioSettings.TechnologyPreference` to `lte` (LTE preferred, with 3G/2G fallback; override with `/etc/bitra-modem-pref` = any|gsm|umts|lte). With it the preference flips to lte at ~40 s and the modem ends on LTE in 3/3 test boots (150 s timelines). Remaining cosmetic issue: a short GSM blip (~5 s, once or twice, between 42 s and 61 s) right after the correction while the modem re-searches; the pref also bounces umts->lte once at ~30 s in one boot, so something else in ofono/the binder plugin still writes `umts` early. Root cause inside ofono-binder-plugin (why the saved preference is not applied / why it starts as umts) not investigated. The Settings label "2G, 3G, 4G preferred" is just ModemManager's rendering of ofono's `lte` (LTE preferred with fallback); there is no "4G only" mode in this stack.

- **Vendor AIDL HAL aborts** (fixed 2026-11-19, rebuilt into the images, not yet flashed): ~300 `received signal 6` per boot from vibrator, lights, rpmh, cammidas, misc, performance, engineer, ... (`Check failed: status == STATUS_OK` in `AServiceManager_addService`). Cause: Android 11's `servicemanager` refuses an AIDL service that is not declared in the VINTF manifest (`servicemanager: Could not find X/default in the VINTF manifest`), and `vintf_sanitize.py` had *deleted* every AIDL `<hal>` to get past the `<version>1</version>` parse error. Dead ends, tested on the phone: dropping `<version>`, or rewriting `<fqname>` as `<interface><name/><instance/>`, makes the whole device manifest unparseable (every HIDL HAL then fails with "must be in VINTF manifest", Phosh dies; recover by restoring the overlay and rebooting). The container's `vintf` tool does not show the device HALs even for a working manifest, so the only oracle is a reboot and `logcat | grep "must be in VINTF"`. After the fix: 0 aborts, Wi-Fi/Bluetooth unaffected.

## Wi-Fi route root cause (2026-11-18, found with bitra-agent)
- NM trace (`nmcli general logging level TRACE domains PLATFORM,IP4`, then `nmcli device reapply`): `do-add-ip4-route[192.168.1.0/24 dev wlan0 ... scope link]: failure 101 (Network is unreachable - Nexthop has invalid gateway)`; the default route then fails for lack of the on-link route. NM retries failed objects after 10 s (the "10 s gap" and the late warning).
- That kernel message only comes from the gateway branch of `fib_check_nh()` (net/ipv4/fib_semantics.c). A raw netlink replay (scratch script, veth pair) showed a subnet route with the NM message shape is accepted, but the same request with `RTA_GATEWAY=0.0.0.0` fails with exactly -101. This 4.19 tree has the 5.x-style `fc_gw_family` handling (set whenever the attribute is present), so a zero gateway is looked up as a real nexthop and fails unless some default route already exists (which is why it was timing dependent: it worked when e.g. a cellular default route was up).
- Fix: `net/ipv4/fib_frontend.c` `rtm_to_fib_config()`: ignore an all-zero `RTA_GATEWAY` (pre-5.2 semantics). Kernel branch `droidian`. Verified: two RAM boots (`ramboot`) with `bitra-net-watch` disabled: NM installs `192.168.1.0/24` and the default route itself, 0 "unable to configure IPv4 route" warnings.
- NM itself was never seen emitting the zero gateway (no strace on the phone); the evidence is the identical error from the replay plus the fix working.
- Side findings: (1) udev sometimes renames `wlan0` to `wlp1s0` (predictable names, race; p2p0/wifi-aware0 collide) - `bitra-net-watch` is hard-coded to wlan0; consider `net.ifnames=0` or a .link file. (2) `example.com` does not resolve on the user's home router (UDP DNS to the router/1.1.1.1/8.8.8.8 all time out for that name only); other names, NTP and HTTPS work. Not a phone bug.
- Done: boot-gz.img (sha 4fff6165…) flashed with `bitra-agent flash boot`; `bitra-net-watch` dropped from scripts/build_droidian_install.py; new userdata.img d7cd1359… (not flashed; the running phone has the service removed live).

## Wi-Fi interface rename (2026-11-19)
- cnss_pci creates three netdevs at once: `wlan0`, `p2p0`, `wifi-aware0`. systemd's `99-default.link` (`NamePolicy=keep kernel database onboard slot path`) gives all three the same path name `wlp1s0`; the first udev worker wins, the others log `Failed to rename ... File exists`. Journal of 10 boots: nearly every boot had the race; some left wlan0 renamed to `wlp1s0` (NM then handles it, but anything hard-coded to wlan0 breaks).
- Fix: `/etc/systemd/network/10-bitra-wlan.link` (`[Match] OriginalName=wlan0 p2p0 wifi-aware0`, `[Link] NamePolicy=keep`). Added to scripts/build_droidian_install.py. Verified live (live-patch + 4 reboots): always `wlan0 p2p0 wifi-aware0`, 0 rename failures.

## Bluetooth name (2026-11-19)
- Symptom: remote devices show the BD address instead of "Droidian for Bitra", although bluetoothctl/BlueZ show the right Name/Alias.
- btmon: right after reset the chip's local name is empty (`Read Local Name -> Name:`); the kernel never sends `Write Local Name (0x0c13)`; BlueZ's later `Set Local Name` with the same value returns early (`set_local_name`: name unchanged). EIR/class are re-sent through Add UUID, so only the name stayed empty. Writing the name raw (`hcitool cmd 0x03 0x0013 ...`) works and `hciconfig hci0 name` shows it.
- Cause: `powered_update_hci()` (net/bluetooth/hci_request.c) queues the LE advertising setup first. The controller answers `LE Set Extended Scan Response Data` with status 0x12 (Invalid HCI Command Parameters); the HCI core drops the rest of the request, including the BR/EDR block (scan, class, **name**, EIR).
- Fix: move the BR/EDR block before the LE block in `powered_update_hci()`. RAM-boot verified (kernel #6): name present after boot, after `bluetoothctl power off/on`, and after `systemctl restart bluetooth` (btmon shows `Write Local Name ... Status: Success`). The user still has to confirm that a remote device now shows the name. The LE ext-adv rejection itself is not understood, but it no longer occurs: on 2026-11-19 a full power off/on cycle showed 48/48 HCI commands `Status: Success` in btmon. **BLE advertising verified**: `bluetoothctl advertise on` (+ `advertise.name on`) sends Extended Advertising Parameters/Data/Scan Response/Enable (legacy ADV_IND PDUs), all Success, and LightBlue on a second phone sees "Droidian for Bitra" (user-confirmed). Scanning and BLE connections are still untested.

## Bluetooth Settings toggle (2026-11-19)
- Settings (gnome-control-center 48 / gsd) switches Bluetooth off by soft-blocking rfkill (both `bt_power` and `hci0`, no BlueZ call) and on by unblocking plus `Properties.Set Powered=true`, retried about once a second. Phosh QuickSettings uses BlueZ `Powered` directly, hence it always worked.
- The kernel's `bt_power` rfkill (`drivers/bluetooth/bluetooth-power.c`, `bluetooth_toggle_radio`) called `bluetooth_power(!blocked)`, cutting the chip's regulators/GPIOs while BlueZ was closing the adapter through bluebinder and the Android BT HAL, which owns that power via /dev/btpower. The HAL hung, init killed it (signal 9), bluebinder logged "Remote has died, trying to reconnect", and the adapter only came back after the HAL restarted (2-5 s) - racing Settings' retries. Replaying only `hci0` block/unblock: adapter back in ~2 s, HAL untouched.
- Power question (measured with a `pr_info` in `bluetooth_power()`): the HAL powers the chip on (`on=1`) and then into retention (`on=2`) at init and never calls `on=0` on close, so blocking only `hci0` leaves the chip in retention; the old rfkill path was the only caller of the full power-off (`on=0`). Likely small saving (Wi-Fi shares the QCA6390 rails vdd-aon/rfa1/rfa2), not measured. Decision (user): keep reliability, make the rfkill handler a no-op (state tracking only). If standby drain with Bluetooth off ever matters: power the chip off after hci0 closed and back on before the next open.
- The driver now also logs every `bluetooth_power()` request with the caller (`bluetooth_power: request on=N by comm[pid]`).
- Verified (RAM boot, kernel #8): 3 Settings off/on cycles incl. 2-3 s gaps, each back on within ~1 s, no HAL kill.
